## E1 · CI 排队与耗时（原 F15）

**结论（已证实）：排队 ≈ 0；单次全流程 4–6 分钟；但 CI 当前「三 job 全红」，不能当绿灯用。**

### 实测（run `39902021644`，2026-10-23，`fix: CAST…`）

| Job | 起止（UTC） | 时长 | 结论 | 失败原因 |
|---|---|---|---|---|
| Formatting | 04:45:30 → 04:45:43 | **~13s** | ❌ | `cargo fmt --check` 多文件 Diff（expression/planner/lib/insert/bloom_filter…） |
| Clippy | 04:45:30 → 04:46:44 | **~74s** | ❌ | `error[E0034]` **第三方** `arrow-arith 52.2.0` × `chrono 0.4.45`（`temporal.rs` / `traits.rs`） |
| Build & Test | 04:45:30 → 04:49:24 | **~3m54s** | ❌ | 见下 |

**排队**：`startedAt == createdAt`（例：`04:45:27Z` 创建 / `04:45:30Z` 开跑）→ **GitHub 排队可忽略**。  
**物理串行点是「测试/编译时长 + 人工 merge」，不是 runner 排队。**（材料推断→已由 E1 证实）

### Build & Test 内部真相（关键）

| 步骤 | 结果 |
|---|---|
| `cargo test`（默认 feature） | ✅ **1229 passed / 0 failed / 4 ignored**（lib + tests 全绿） |
| `cargo test --features datafusion` | `continue-on-error`（E0034 再现，非阻塞） |
| `cargo build --benches` | ❌ **编译失败**：`E0716` 临时值借用、`E0499` 重复 `&mut`、`E0596` 非 mut 借用（bench 目标存量错误） |

→ **「默认测试」在 CI 是绿的；红的是 fmt、clippy、benches 编译。**  
→ 评审原文“CI 排队&gt;2h 降级”阈值 **过时**：应改为“**fmt/benches 红则不算单一可信链**”。

### 近 30 次 push 结论分布（gh run list）

| 结论 | 次数（目测/抽样） |
|---|---|
| success | **1**（`34002438362` 2026-09-06 mmap_read_bench cfg 修复） |
| failure | **29**（含 docs-only push） |

**含义**：历史 CI 长期红；「以 CI 绿为完成定义」必须先 **修绿 CI 基线**（至少 fmt + default test + benches 编译），否则 Agent 的“CI 绿”标准不可执行。

**对 Q1 的修订建议**：并行度瓶颈不是排队，而是 **Lead 合并带宽 + 红基线干扰**。维持 3 路仍合理；切换条件改为「**连续 2 个 Agent 的 PR 因 merge 冲突 &gt;1h**」。

**Owner**：A-Infra · **验收**：本文件 + 一次修绿 run id 贴入决议表。

## E4 · 列存 DELETE × 压缩段 设计风险列表（原 H3 前置）

**结论（材料推断，静态代码映射；实现前需 A-Storage 半页设计确认）**

### 现状（已证实）

| 层 | 删除能力 | 位置 |
|---|---|---|
| Delta 行存 | ✅ `delete_delta_rows`（tombstone set） | `table.rs:2736` |
| 向量索引 | ✅ HNSW tombstone | `vector_index.rs` |
| **列存 RowGroup** | ❌ **无 delete API**；只有 `append_*` / `read_column` / `ensure_rg_decompressed` | `column_store.rs` |
| Compact | `compact_delta` / `maybe_compact` / `compact_delta_partial` | `table.rs:2055,2603,2664` |

### 风险清单（DELETE 设计必答）

| ID | 风险 | 为何危险 | 设计必须回答 |
|---|---|---|---|
| R1 | **压缩 RG 与 tombstone 位图不一致** | 按行删会解压整 RG，退化为行存 | tombstone 存在 RG 外还是段文件旁路？读路径 `ensure_rg_decompressed` 是否跳过全死 RG？ |
| R2 | **min/max / 稀疏索引失效** | 删最值行后 `estimate_skip` 仍跳读 → 漏行/错行 | 何时重算统计：标记时 or compact 时？ |
| R3 | **PK 定位 `locate_pk` 命中已删行** | 点查返回幽灵或空洞 | delete 与 sparse/primary 索引同步顺序 |
| R4 | **compact 后 row_id 重排** | MVCC/向量索引/差分测试以 row_id 为键 | 保 row_id 还是维护 remap？`test_compact_preserves_row_id_read` 已有约束 |
| R5 | **崩溃后 tombstone 丢失** | 已删行复活 = 数据正确性事故 | tombstone 是否走 WAL；恢复优先级 |
| R6 | **列存格式版本** | 旧 `.hdb` 读新 tombstone 段 | 文件头版本位；拒绝/降级策略（不可逆点） |
| R7 | **与 `delete_row`（memory engine）语义分叉** | 同名不同义，测试口径乱 | 统一 `EngineTable` 删除契约 |
| R8 | **压缩 recommender / TokenDelta 缓存** | 以为行还在，字典/缓存膨胀 | compact 时是否重建压缩决策 |

**阶段门（配合 H3=C）**：
1. **阶段1**：逻辑 tombstone + 读过滤（可查证、可 revert）→ 关闭 R1/R2/R3 读侧  
2. **阶段2**：compact 物理回收 + 空间断言 → 关闭 R4/R8  
3. **全程**：WAL/恢复用例 → R5；版本位 → R6（签字前必须写明）

**Owner**：A-Storage（设计）/ Lead（签字） · **验收**：半页设计含 R1–R8 表 + 阶段1测试绿。
