## 2. 一句话结论

分层意图清晰（`common → storage/txn/wal → sql/executor → lib` 门面），但图上真实结构是 **以 `storage::Database` 为万能枢纽的星型 + `sql↔executor` 双向厚边**；最大正确性/演进风险仍是三个超大文件与 `Database`/`PhysicalPlan` 的扇入，不是某个叶子算法写错。

## 8. 读/写路径（对照依赖图）

**写路径**

```
Connection::execute / prepared
  → sql::{parser → planner → optimizer}     [依赖 Database: catalog/statistics]
  → executor::execute(PhysicalPlan, &mut Database)
      → operators::{insert,update,delete}
          → storage::insert_batcher / Table / DeltaStore
          → txn::{TransactionManager, MVCC}
          → wal::WalWriter（组提交）
```

图证据：`insert.rs → Database` 12 条；`Database → TransactionManager`；`txn → wal` 净 +11。

**读路径**

```
plan（可命中 Database.plan_cache）
  → table_scan（sparse / bloom skip）
  → filter / projection / aggregate / join / sort …
  → DataChunk 向量化 → QueryResult
```

图证据：`planner ↔ physical_plan` 49；`expression ↔ vector` 67；search 簇仅在 `table.rs→sparse` 挂入。

**检索旁路**：`search/*` → `common::tokenizer`；`storage::table` → `search::sparse`。未深度接入 executor 算子（与既有文档「多为纯函数、未算子化」一致）。

## 9. 结构问题（按图排序）

1. **`Database` 是上帝对象（度 200）**  
   承载表注册、plan_cache、统计、txn_manager、攒批、分层迁移……sql/executor/txn 全部扇入。改存储语义会牵动规划与执行。

2. **`sql ↔ executor` 边界对称耦合（127 vs 119）**  
   `expression.rs` 直接 `use crate::sql::ast`；planner 直接产出 `PhysicalPlan`。缺中间「计划 IR」或单向依赖约束。

3. **`storage ↔ txn` 环 + insert 回写环**  
   `transaction.rs` 调用 `operators::insert::apply_to_storage`，事务与 DML 实现互相咬合。

4. **三巨型文件**  
   `expression` / `planner` / `lib`（+ `table`）承载过多测试与历史分支，图上自环边权极高（同文件 500+）。

5. **`buffer_pool` 死代码**  
   仅自引用 + `#[deprecated]`；图上无生产扇入。对应 `config.buffer_pool_size` 应一并清。

6. **`datafusion_ext` 旁路未闭环**  
   只向下依赖 storage/common；catalog 仍 `TODO` 加载表，谓词下推未接——图上是干净的可选叶子，但功能未完成。

7. **文档/基准噪声进图**  
   325 社中大量 md 社区（路线图、Phase 报告）；分析生产代码时需按 `source_file` 前缀过滤（本文字已过滤）。
