# 单文件数据库并行 Compact 调度问题分析

**版本**: v0.11.2  
**日期**: 2026-08-02  
**范围**: EngramDB 列存引擎 Delta→ColumnStore 合并调度策略

---

## 1. 问题背景

### 1.1 Compact 是什么

在 EngramDB 的 LSM-tuple 架构中，写入分为两层：

- **DeltaStore**：内存列式缓冲，吸收随机写入，低延迟
- **ColumnStore**：磁盘列存主存储，按 Row Group 组织，支持压缩和索引

当 DeltaStore 积累到一定阈值时，需要将数据合并（Compact）到 ColumnStore 中。这个过程包括：
1. 将 Delta 的列式数据追加到 ColumnStore 的 Row Group
2. 清空 DeltaStore
3. 更新表元数据（行数等）

### 1.2 为什么需要"并行"

在传统 LSM-Tree 数据库（如 LevelDB、RocksDB）中，Compaction 由后台线程异步执行，前台写入不受影响。但 EngramDB 是**单文件嵌入式数据库**，架构约束完全不同：

- **单线程模型**：嵌入式库，没有后台线程池
- **单文件 I/O**：所有数据在一个文件中，不存在多文件并行写入的可能
- **无独立进程**：与应用在同一进程地址空间，不能 fork 后台 worker

因此"并行 compact"在这个架构下需要重新定义——不是多线程并行，而是**调度策略的优化**：何时触发、每次合并多少、如何减少对前台操作的阻塞。

## 2. 核心约束分析

### 2.1 单文件约束

| 约束 | 影响 |
|------|------|
| 单一文件句柄 | 读和写不能同时进行（pread/pwrite 虽可并发但需同步） |
| 连续空间分配 | 新增 Row Group 只能追加到文件末尾，无法"并行写入"不同区域 |
| 无目录结构 | 不能通过多文件并行读写来提升吞吐 |

**结论**：单文件架构下，I/O 层面的真正并行是不可能的。所有 compact 操作必然与前台读写竞争同一个文件句柄。

### 2.2 单线程约束

| 约束 | 影响 |
|------|------|
| 无后台线程 | Compact 必须在某个前台调用的上下文中执行 |
| 阻塞式执行 | 一旦开始 compact，当前线程会被阻塞直到完成 |
| 无抢占机制 | Compact 中途不能被暂停来服务前台查询 |

**结论**：单线程模型下，compact 的调度本质是"在哪个前台操作中、以多大粒度执行"的问题。

### 2.3 MVCC 事务约束

| 约束 | 影响 |
|------|------|
| 快照隔离 | 活跃事务可能持有 Delta 数据的快照，不能随意清除 |
| 写-写冲突检测 | Compact 期间不能影响正在进行的事务写入 |
| 版本链管理 | Delta 数据合并到列存后，MVCC 版本链需要保持连续 |

**结论**：Compact 不能简单地"搬数据"，需要与事务管理器协调，确保活跃事务的快照一致性。

## 3. 现有方案评估

### 3.1 当前实现

当前 EngramDB 的 compact 触发策略：

```rust
// 在 Table::insert 中
if self.delta_store.len() >= self.def.row_count as usize + 10000 {
    self.compact_delta()?;
}
```

**触发条件**：Delta 行数 >= 表总行数 + 10000

**问题分析**：

1. **触发时机不合理**：条件为 `delta.len() >= row_count + 10000`，意味着：
   - 空表时，写入 10000 行触发一次 compact
   - 100 万行的表，需要再写入 1,010,000 行才触发
   - 大表的 Delta 层会无限膨胀，查询性能持续下降

2. **同步阻塞**：在 insert 调用中直接执行 compact，前台写入会被阻塞
   - 小表 compact 很快（毫秒级）
   - 大表 compact 可能需要秒级甚至更长
   - 写入延迟抖动严重

3. **全量合并**：每次 compact 把整个 Delta 全部合并
   - 没有增量合并选项
   - Delta 越大，单次 compact 时间越长
   - 延迟抖动越严重

4. **无事务感知**：compact 直接操作数据，不考虑活跃事务
   - 如果有事务正在读 Delta 数据，可能导致快照失效
   - 当前 MVP 阶段事务与存储层解耦，问题不明显
   - 未来完整 MVCC 集成后会出问题

### 3.2 性能影响估算

假设场景：10 列 Int64 表，每行 ~80 字节，Delta 积累 100 万行

| 操作 | 估算耗时 | 说明 |
|------|---------|------|
| Delta 列式追加到列存 | ~5-10ms | 纯内存 memcpy，100 万行 × 10 列 |
| MinMax 索引更新 | ~2-5ms | 遍历每列更新统计 |
| 压缩（如果启用） | ~50-200ms | 取决于压缩算法 |
| 持久化到磁盘 | ~10-50ms | 80MB 数据，取决于磁盘 |
| **总计（内存态）** | **~7-15ms** | 未压缩、未落盘 |
| **总计（落盘+压缩）** | **~60-260ms** | 完整持久化 |

**结论**：纯内存态的 compact 很快（毫秒级），但如果涉及压缩和磁盘 I/O，延迟会显著增加。对于交互式工作负载，超过 100ms 的阻塞是不可接受的。

## 4. 可选方案对比

### 方案一：增量式 Compact（Incremental Compact）

**思路**：每次只合并 Delta 的一部分，而不是全量合并。

**实现方式**：
- 将 DeltaStore 内部分为多个"段"（segment）
- 每次 compact 只合并一个段到列存
- 分多次完成全部合并，每次阻塞时间更短

**优点**：
- 单次阻塞时间可控（可配置段大小）
- 写入延迟更平稳
- 实现相对简单

**缺点**：
- 总耗时更长（多次小合并 vs 一次大合并）
- Delta 层数据结构更复杂
- 查询时需要扫描更多段

**适用场景**：交互式工作负载，对延迟敏感

---

### 方案二：读侧合并（Read-side Merge）

**思路**：借鉴 LSM-Tree 的 compaction 思路，不在写入时触发 compact，而是在读取时渐进式合并。

**实现方式**：
- 写入永远只写 Delta，不主动触发 compact
- 扫描时，如果发现 Delta 过大，"顺便"合并一部分到列存
- 类似 LevelDB 的"seek compaction"

**优点**：
- 写入路径永远低延迟
- 读多写少场景下自动适配
- 不需要后台线程

**缺点**：
- 读延迟不稳定（某些读会触发合并）
- 写密集场景下 Delta 无限膨胀
- 实现复杂度高

**适用场景**：读多写少、写入延迟要求极高

---

### 方案三：显式 Compact（Explicit Compact）

**思路**：不自动触发 compact，完全由用户控制。

**实现方式**：
- 提供 `connection.compact(table_name)` API
- 用户在业务低峰期手动调用
- 类似 SQLite 的 `VACUUM` 或 Redis 的 `BGREWRITEAOF`

**优点**：
- 最灵活，用户完全掌控
- 不会在意想不到的时候阻塞
- 实现最简单

**缺点**：
- 需要用户理解内部机制
- 忘记调用会导致 Delta 膨胀、查询变慢
- 不适合"即开即用"的嵌入式场景

**适用场景**：批量导入后、ETL 作业、高级用户

---

### 方案四：自适应阈值 + 分桶合并

**思路**：结合方案一和当前方案，使用自适应的触发阈值和分桶式合并。

**实现方式**：
- 触发阈值：`min(delta_size, row_group_size * N)`，有上限
- 合并粒度：按 Row Group 为单位合并，每次最多合并 M 个 Row Group
- 写入路径：检查 Delta 大小，超过阈值则合并一个 Row Group 的量

**优点**：
- 单次阻塞时间上限可控（一个 Row Group 的量）
- 大表不会出现 Delta 无限膨胀
- 自动适配不同表大小
- 实现复杂度适中

**缺点**：
- 写入路径多了一次阈值检查（开销极小）
- 小批量写入场景下总合并次数更多

**适用场景**：通用场景，EngramDB 的推荐方案

---

### 方案五：异步 WAL 模式下的批量 Compact

**思路**：利用 Periodic WAL 刷盘模式，在用户调用 `sync_wal()` 时顺便执行 compact。

**实现方式**：
- 用户使用 Periodic 模式，定期调用 `sync_wal()`
- `sync_wal()` 内部除了刷盘，还检查并执行 compact
- 将两次 I/O 操作合并，减少系统调用次数

**优点**：
- I/O 合并，效率更高
- 与 WAL 刷盘周期对齐，调度更合理
- 不增加额外的阻塞点

**缺点**：
- 只在 Periodic 模式下有效
- Sync 模式下不适用
- compact 频率取决于刷盘频率

**适用场景**：使用 Periodic WAL 模式的批量写入场景

## 6. 推荐方案：自适应分桶 + 显式 Compact 组合

### 6.1 核心策略

**默认策略：自适应分桶合并**

```
触发条件：
  delta_rows >= min(row_group_size, max(10000, table_rows * 0.1))
  即：Delta 行数达到 row_group_size 或表行数的 10%（取较小者，下限 10000）

合并粒度：
  每次合并一个 Row Group 的数据量（~120K 行）
  如果 Delta 剩余量仍超过阈值，下一次写入继续合并

阻塞上限：
  单次 compact 阻塞时间 ≈ 5-20ms（内存态）
  最坏情况（压缩+落盘）≈ 50-100ms
```

**补充策略：显式 Compact API**

```rust
impl Connection {
    /// 手动触发表的 Delta 合并
    pub fn compact(&mut self, table_name: &str) -> Result<u64>;
    
    /// 合并所有表的 Delta
    pub fn compact_all(&mut self) -> Result<u64>;
}
```

用户可以在批量导入后或业务低峰期手动调用。

### 6.2 与 WAL 刷盘策略的联动

| WAL 模式 | Compact 策略 | 说明 |
|---------|-------------|------|
| Sync | 自适应分桶 | 每次 commit 都 fsync，compact 独立调度 |
| BufferFull | 自适应分桶 | 缓冲区满时自动 flush，compact 独立触发 |
| Periodic | 批量 Sync 合并 | sync_wal() 时顺便检查并执行 compact |

Periodic 模式下的优化：`sync_wal()` 内部先刷 WAL，再检查 Delta 阈值，需要时执行 compact。将两次磁盘 I/O 合并到同一个"同步点"。

### 6.3 事务安全保证

Compact 执行前需要检查活跃事务：

1. 获取最老活跃事务的 start_ts
2. 如果 Delta 中所有数据的写入时间都早于最老活跃事务的 start_ts → 可以安全合并
3. 否则 → 只合并早于 start_ts 的部分，保留新版本

当前 MVP 阶段事务与存储层解耦，这个检查可以延后实现。完整 MVCC 集成后必须加上。

- 使用 `tokio` 或 `async-std` 支持异步 compact
- 单线程并发（cooperative multitasking）

- 类 RocksDB 的后台 compaction
- 对于服务器端部署场景可选启用
- 保持默认单线程嵌入式模式

## 8. 结论

### 8.1 核心判断

**单文件嵌入式数据库不存在真正的"并行 compact"**——这是由架构本质决定的：

1. **单文件** → I/O 无法并行（所有操作竞争同一个文件）
2. **单线程** → CPU 无法并行（没有后台线程）
3. **嵌入式** → 不能假设用户允许开线程

因此，所谓"并行 compact 调度"实际上是**阻塞时间管理**问题——如何让 compact 对前台操作的影响最小化。

### 8.2 关键发现

1. **列式 Delta 已经大幅降低了 compact 开销**：P4 优化后，Delta→列存合并是纯列式追加，不需要行→列转置，100 万行数据仅需几毫秒（内存态）

2. **真正的瓶颈在磁盘 I/O 和压缩**：如果 compact 时需要压缩和落盘，时间会增加一个数量级

3. **分桶合并是性价比最高的方案**：用很小的实现复杂度，换取可控的阻塞时间

4. **显式 API 是必要的安全网**：给高级用户完全控制权，应对极端场景

### 8.3 实施建议

| 优先级 | 事项 | 预估工作量 |
|--------|------|-----------|
| P0 | 修复当前触发条件 bug（`row_count + 10000` 改为比例阈值） | 0.5 天 |
| P0 | 实现 `compact()` / `compact_all()` 显式 API | 0.5 天 |
| P1 | 自适应分桶合并（按 Row Group 粒度） | 1 天 |
| P1 | Periodic WAL 模式下 sync_wal() 联动 compact | 0.5 天 |
| P2 | 事务感知 compact（MVCC 版本检查） | 2 天 |
| P3 | 异步 I/O 支持 | 3-5 天 |

**建议立即实施 P0 项**（修复触发条件 + 显式 API），投入小但收益明显。P1 项可在下一迭代中完成。
