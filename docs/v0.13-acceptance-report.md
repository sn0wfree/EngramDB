## 关键技术修复

### 1. setup 超时（177s+ → 0.6s）

**原因**：原 setup 用 SQL 单行 INSERT 1M 行，每行解析+规划开销巨大。

**修复**：使用 `import_columns` API 直接列式写入，绕过 SQL 解析层：
- EngramDB：177s+ → **634 ms**
- SQLite：加 PRAGMA + 批量 50K → **1.07 s**

### 2. `plan_with_params` SELECT 参数替换缺失

**原因**：`plan_with_params` 原来只处理 INSERT 参数，SELECT/DELETE/UPDATE 的 WHERE 子句中 `Placeholder` 未替换，导致 executor 报错。

**修复**：添加 `substitute_params_expr` / `substitute_params_stmt` 递归替换所有 `Expression::Placeholder(idx)` → `Expression::Literal(params[idx])`。

### 3. A-2 bench hang（TableNotFound "t"）

**原因**：`setup_sqlite_1m()` 在开头调用 `cleanup_files()`，但 `cleanup_files()` 会删除**所有**文件（包括 HDB 文件）。结果 `a2_setup_engramdb()` 刚创建的 HDB 文件被 SQLite setup 误删。

**修复**：`setup_sqlite_1m()` 改为只清理 SQLite 文件：
```rust
fn setup_sqlite_1m() {
    let _ = std::fs::remove_file(SQLITE_PATH);
    let _ = std::fs::remove_file(format!("{}-wal", SQLITE_PATH));
    let _ = std::fs::remove_file(format!("{}-shm", SQLITE_PATH));
    // ...
}
```

### 4. PrimaryKeyLookup 列裁剪（Perf03 增强）

**原因**：`PhysicalPlan::PrimaryKeyLookup` 原本只读全列（`for col_idx in 0..num_cols`），即使 SELECT 只查询部分列。`table.def.columns.len()=3`，每查询读 50K × 3 = 150K Value 条目。

**修复**：
- `PhysicalPlan::PrimaryKeyLookup` 增加 `output_column_indices: Vec<usize>` 字段
- planner.rs 创建时传入 `scan_column_indices`（去掉 PK 时全列覆盖的逻辑）
- executor.rs 只读指定列
- 新增 `Table::get_row_by_id_columns(row_id, col_indices)` 按列裁剪读取

### 5. 列存压缩 → 索引点查基准

**问题**：`compress_on_persist: true`（默认）下，`close()` 触发 `compress_all()`。下次 reopen 时数据以压缩态加载，`read_column` 首次访问时惰性解压（每列 ~1.5ms）。1M 行表有 20 row group × 3 列 = 60 个列块，每轮 reopen 都会触发 18 次左右解压 → A-2 平均延迟被拖累到 30µs/query。

**解决方案**：bench 使用 `Config { compress_on_persist: false, .. }`：
```rust
fn open_hdb() -> Connection {
    let config = Config {
        compress_on_persist: false,
        ..Config::default()
    };
    Connection::open_with_config(HDB_PATH, config).unwrap()
}
```

注意：这是**基准配置**，不是产品改动。生产环境可根据存储成本/查询延迟权衡决定。
