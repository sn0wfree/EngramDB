# Phase 1.4 — C04 Column-Level UNIQUE

## Summary

Added support for column-level `UNIQUE` constraints in `CREATE TABLE`, enabling the SQL syntax `col_name TYPE UNIQUE` to enforce uniqueness without requiring a separate `CREATE UNIQUE INDEX` statement.

## Changes

### Parser (`src/sql/parser.rs`)

- `parse_column_def` detects `ColumnOption::Unique { is_primary: false }` from sqlparser AST
- Sets `ColumnDef.unique = true` for non-primary UNIQUE columns

### Planner (`src/sql/planner.rs`)

- `plan_create_table` iterates columns; for each `unique && !primary_key` column, creates an `IndexDef` with name `uniq_{table}_{col}`, single key column, unique=true

### Storage (`src/storage/table.rs`)

- `Table::create_index` now guards against duplicate index definitions: only pushes to `self.def.indexes` if no index with the same name exists
- This prevents `Database::create_table` from adding a duplicate entry when the index was already added by the planner

### Storage (`src/storage/mod.rs`)

- `Database::create_table` unchanged — continues to call `create_index` for unique indexes, which now safely handles pre-existing definitions

## Bug Fixed

**Root cause of first-INSERT failure**: `Database::create_table` called `Table::create_index` for each unique index in `def.indexes`. Since `create_index` unconditionally pushed to `self.def.indexes`, this created a duplicate entry. When `update_indexes_for_row` iterated `def.indexes`, it called `insert_with_included` twice for the same key — the first succeeded, the second detected a duplicate and returned false, causing a spurious `ConstraintViolation` error.

**Fix**: Added `if !self.def.indexes.iter().any(|i| i.name == index_name)` guard in `create_index`.

## Tests

- `test_unique_column_constraint`: CREATE TABLE with `id INT UNIQUE`, INSERT (1,'a') succeeds, INSERT (1,'b') fails with UNIQUE violation
- `test_unique_column_with_pk`: CREATE TABLE with `id INT PRIMARY KEY, name VARCHAR UNIQUE`, verifies PK and UNIQUE constraints work independently
