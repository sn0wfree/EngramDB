## 验收项覆盖分析

| 验收项 | 现有覆盖 | 缺口 | 缺口类型 |
|---|---|---|---|
| **A-1 事务写入** | ❌ 完全缺失 | 数据规模 + 事务路径 + SQLite 对比 | 三重缺失 |
| **A-2 索引点查** | 🟡 `compare_bench.py` 有 100k 行 | 数据规模 100k → 1M | 数据规模不足 |
| **A-3 COUNT(*)** | 🟡 `compare_bench.py` 有 100k 行 | 数据规模 100k → 1M | 数据规模不足 |

### 缺口根因

1. **A-1 事务写入缺口**：
   - 现有 `write_bench.rs` 用 `conn.execute(sql)` 逐条插入，但走的是 SQL 路径而非事务路径（默认走单行事务）
   - 现有 `compare_bench.py` 用 `executemany` 批量插入，**未走事务**（SQLite 走 autocommit，EngramDB 走 autocommit）
   - 无任何基准对比两个引擎在显式 BEGIN/COMMIT 包裹下的写入吞吐

2. **A-2 / A-3 数据规模不足**：
   - 路线图预期 100 万行，验证「性能懒加载/索引随规模变化」曲线
   - 100k → 1M 跨越 10× 数据量，是 OLTP 性能分水岭

3. **公平性缺口**：
   - Python 基准有 Python sqlite3 vs Python EngramDB 不可比（EngramDB 无 Python 绑定）
   - 当前做法：Python 用 sqlite3 直接对比，EngramDB 走 mongosh 样的 HTTP 子进程 → 不在基线内
   - **最佳公平对比**：Rust crate `rusqlite` vs `engramdb` 直接 API 调用

## 补全方案（Block 1.2 输入）

### 推荐方案：Rust 基准 `benches/v0.13_acceptance_bench.rs`

**理由**：
- 同一进程同时持有 EngramDB 和 SQLite 连接，避免 Python FFI 开销差异
- 直接 `Connection` API 调用（公平的"应用层"开销）
- 可加入 [dev-dependencies] `rusqlite = { version = "0.31", features = ["bundled"] }`（bundled 模式自带 SQLite 库，无需系统依赖）

**Cargo.toml 变更**：
```toml
[dev-dependencies]
tempfile = "3.0"
criterion = "0.5"
rusqlite = { version = "0.31", features = ["bundled"] }   # 新增
```

**v0.13_acceptance_bench.rs 测试矩阵**：

| 编号 | 场景 | EngramDB 路径 | SQLite 对比 | 数据规模 | 重复次数 |
|---|---|---|---|---|---|
| **A-1** | 事务内逐行插入 | `conn.begin()` + loop + `conn.commit()` | `conn.transaction()` + `execute()` × N | 1000 事务 × 1 行 = 1000 行 | 5 次 |
| **A-2** | 主键点查 | 100w 行表，随机等值 10000 次 | 同 | 1M 行 | 5 次 |
| **A-3** | COUNT(*) 无 WHERE | 100w 行表 | 同 | 1M 行 | 5 次 |

**a/b/c 变体**：
- A-1a: 事务内单行 INSERT
- A-1b: 事务内批量 INSERT（10/批）

### 备选方案：扩展 `compare_bench.py`

若用户希望零依赖（不加 rusqlite），则扩展现有 Python 基准：
- 优点：避免新增 dev-dependency
- 缺点：EngramDB 需通过 CLI 二进制测试，测量精度低（进程启动开销 50-100ms/次）

**结论**：推荐 Rust 方案。`rusqlite` bundled 模式零系统依赖，1MB 编译开销可接受。
