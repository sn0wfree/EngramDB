# v0.20 约束表进入攒批（主键表逐行 INSERT 10.7x）

> 日期：2026-08-07
> 状态：✅ 已完成（含 3 项决策确认）
> 目标：SQL autocommit 与显式事务内「主键表逐行 INSERT」从 28.7µs/行
> 降到 2.7µs/行（每行独立内部事务 → 攒批单事务），同时保留
> 「约束错误在该语句返回时暴露」的语义

---

## 一、TL;DR

| 项 | 内容 |
|---|---|
| 现象 | 主键表逐行 INSERT 每行开一个内部事务（begin→WAL→MVCC→commit fsync→apply） |
| 根因 | `table_has_constraints`（insert.rs:58）+ `txn_batch_bypass_constraint_tables=true`（config.rs:293）把主键表挡在 Batcher 外 |
| 方案 | 约束表**入批时即校验**（PK / 唯一索引 / NOT NULL），flush 走单事务攒批落盘 |
| 收益 | **实测 10.7x**（28.7µs → 2.7µs/行，autocommit + 显式事务两路）；Transaction API 冲突错误提前到 insert 即报 |
| 顺带修复 | ①批量 apply 静默吞唯一索引冲突 ②delta_store compact 后批量 rowid 脱节 ③显式事务内 PK 插入撤不掉回滚 |
| 排除 | FK / TTL 表仍绕过攒批（保守，后续迭代） |

---

## 二、现状与根因（与代码核对）

### 现状：三路 INSERT 的耗时差异（实测，10 万行 / 4 列 / PK 表）

| 场景 | 单行耗时 | 加速比 |
|---|---|---|
| SQL autocommit 主键表逐行 INSERT | 27,000 ns | 1.0x |
| Prepared Statement（省解析） | 24,430 ns | 1.15x |
| Transaction API `txn.insert`（已攒批） | 2,870 ns | 9.4x |
| Batcher + 无主键 | 2,290 ns | 11.8x |

### 根因链

```text
SQL INSERT（主键表）
  ├─ autocommit: insert.rs:58  !table_has_constraints → false → 绕过 Batcher
  │    → execute_with_txn 每行：begin → 预检 → batch_insert(WAL) → commit(fsync) → apply
  └─ 显式事务(BEGIN): insert.rs:72-76  txn_batch_bypass_constraint_tables=true
       → 主键表绕过 txn_buffer → 同样每行一个内部事务
Transaction API 不受影响：transaction.rs:79 直接 txn_buffer_push（无约束门控）
```

**27µs 里 21.5µs（79.9%）是每行一个内部事务的固定开销**，攒批后只剩
预检 + 存储写入 ~2.9µs/行。

## 三、为何安全（风险已评估）

1. **入批即校验**：冲突在语句返回时暴露（零副作用，不落批），与现状语义一致
2. **兜底双保险**：flush 仍走 `execute_with_txn` 预检（整批一次、摊薄）；
   apply 侧 PK 检查照旧（auto_increment 保留，commit 806d89d 已保证）
3. **单线程模型**：push 与 flush 之间无并发写入（`&mut Database`），
   预检结果在 flush 时依然有效
4. **批内自重复**：`BatchedRows` / txn_buffer 维护常驻 seen-set（O(1) 判重，
   避免逐行扫描 O(N²)）
5. **读己之写**：非裸 INSERT / SELECT / RETURNING / ON CONFLICT 前置
   `flush_batches` 已有，行为不变

## 四、必做的前置修复：批量 apply 静默吞唯一索引冲突

- **现状 bug**：单行 apply 检查 unique 返回值（table.rs:1737），
  **批量 apply 不检查**（`update_indexes_for_rows` table.rs:1772 忽略返回值）
  → 重复键静默丢弃，表与索引不一致
- **为何必须修**：主键表放行攒批后，flush 走 M02/InsertBatch 批量 apply，
  必然踩中该路径
- **修复**：
  1. `update_indexes_for_rows` → 返回 `Result<()>`，unique 插入失败报
     `ConstraintViolation`（insert/insert_columns 调用方加 `?`）
  2. `Table::check_unique_indexes` 预写检查（零副作用，镜像批量 apply 逻辑）
  3. `execute_with_txn` 预检扩展：唯一索引列也批内 seen + 点查

## 五、改动方案

### 1. 前置修复（①号隐患）

| 文件 | 改动 |
|---|---|
| table.rs `update_indexes_for_rows` | 返回 `Result<()>`，unique 失败报错；insert/insert_columns 调用处 `?` |
| table.rs `check_unique_indexes` | 新增：批内 seen + `SkipListIndex.get_entries` 判重（零副作用，写前调用） |
| insert.rs `execute_with_txn` 预检 | 扩展：唯一索引列批内 seen + 点查（整批一次） |

### 2. 门控拆分（insert.rs）

```rust
table_batchable(db, name)     // engine==Columnar && 有 PK/NOT NULL/auto/unique && !FK && !TTL
table_excludes_batch(db, name) // FK / TTL 表（注释记录后续迭代）
```

### 3. 入批校验（两路共用，放 Database）

`validate_batch_rows`：
- 主键：批内 seen-set + `lookup_primary_key`（auto_increment NULL 跳过）
- 唯一索引：批内 seen（`key_columns[0]` 镜像批量 apply）+ `SkipListIndex.get_entries`
- NOT NULL 列非空检查

调用点：
- `txn_buffer_push`（storage/mod.rs:383）内联 → **Transaction API 与 SQL 显式事务共用**
- `insert::execute` autocommit push 前单独调用（对「新行 + batcher 已攒行」）

### 4. seen-set 常驻（防 O(N²)）

- `BatchedRows` 增加 PK / 唯一键 seen-set，push 时 O(1) 判重
- txn_buffer 增加 `txn_buffer_seen`，push 时 O(1) 判重；discard/flush 时清空

### 5. 语义不动

- RETURNING / ON CONFLICT / INSERT...SELECT 仍 bypass（lib.rs:248 batcher_clean）
- 非裸 INSERT / begin / close / checkpoint 前置 flush 已有
- auto_increment PK：入批跳过 NULL（flush 分配，天然唯一）；显式小值由 apply 检查兜底

### 6. 显式事务回滚语义修复（行为修正）

- **现状缺陷**：BEGIN 内主键表 INSERT 走独立内部事务立即提交 → 外层
  ROLLBACK **撤不掉**（各测试文件确认当前行为）
- **改后**：主键行进 txn_buffer → ROLLBACK 正确丢弃（更符合事务语义）
- 需补测试确认无现有测试依赖旧行为

## 七、实测基准（2026-08-07，release，10 万行 / 4 列 / PK 表）

> 临时 bench 已清理；复测口径与用户分析一致。

```
[A] SQL autocommit 逐行（攒批）   : 37.1 万行/秒  每行 2.70 µs   ✅ count=100000
[B] SQL 显式事务逐行（攒批）      : 38.4 万行/秒  每行 2.60 µs   ✅ count=100000
[C] autocommit（关闭攒批，旧行为）:  3.5 万行/秒  每行 28.7 µs
```

- 加速比：**10.7x**（28.7µs → 2.7µs/行），与用户分析的 9-15x 预期吻合
- 两路（autocommit / 显式事务）同时拿到收益，且主键冲突 / 唯一索引 /
  NOT NULL 错误仍在语句返回时即时报错

## 八、实施中发现并修复的既有 bug

### delta_store 批量插入 rowid 基准脱节（本次暴露，必须修）

- **症状**：compact 后批量插入，主键点查错位（id=500 返回 v=2 即 id=1 的行）
- **根因**：`delta_store.clear()`（compact 后调用）把 `next_rowid` 重置为 1，
  而 `Table::insert`/`insert_columns` 小批量路径直接用 delta 内部 `next_rowid`
  作为 rowid 基准 → 与列存行 rowid 重叠，主键索引错乱
- **为何此前未暴露**：主键表绕过攒批 → 每行走显式 rowid 的 `insert_row`；
  攒批 flush 走批量路径后才踩中
- **修复**：`delta_store.set_next_rowid(base_row_id)`，`Table::insert` /
  `insert_columns` / lib.rs import 列式路径在写入 Delta 前对齐 rowid 基准
- **新增回归**：`test_layered_compact_consistency`（compact + 二次批量插入 + 点查）

### 批量 apply 静默吞唯一索引冲突（①号修复）

- `update_indexes_for_rows` 忽略 `insert_with_included` 返回值 → 表与索引不一致
- 修复：返回 `Result`，unique 失败报 `ConstraintViolation`；
  新增写前零副作用检查 `check_unique_indexes`
- **新增回归**：`test_batch_apply_unique_conflict_reported`

### 显式事务内主键插入撤不掉回滚（语义修复）

- 旧行为：BEGIN 内主键表 INSERT 走独立内部事务立即提交 → ROLLBACK 无效
- 新行为：主键行进 txn_buffer → ROLLBACK 正确丢弃
- **新增回归**：`test_rollback_discards_batched_pk_inserts`

## 九、一句话总结

把「主键表绕过攒批」改成「入批即校验 + flush 单事务」：SQL 两路
逐行 INSERT 拿 10.7x（28.7µs → 2.7µs/行），约束错误仍在语句时暴露；
顺带修掉 delta_store 批量插入 rowid 脱节、批量 apply 静默吞唯一索引
冲突两个既有 bug，并修复显式事务内主键插入撤不掉回滚的语义缺陷。
