# EngramDB SQL 策略：复用成熟方案，聚焦执行器

> 核心决策：解析器 + 优化器直接用 DataFusion 生态，EngramDB 专注存储层 + 执行层差异化

---

## 一、核心决策

### 为什么不自研解析器和优化器？

| 模块 | 自研成本 | 成熟方案质量 | 差异化价值 |
|------|----------|-------------|-----------|
| SQL 解析器 | 极高（语法边界多、兼容性要求高） | sqlparser-rs 已被业界广泛验证 | 几乎为零 |
| 查询优化器 | 极高（规则多、成本模型复杂、统计信息体系庞大） | DataFusion 优化器已生产可用 | 低（通用优化各数据库差异不大） |
| **执行器** | 中 | 各数据库差异巨大 | **高（与存储层深度结合是核心竞争力）** |
| **存储引擎** | 高 | — | **最高（压缩/索引是 EngramDB 立身之本）** |

**结论：解析器和优化器用现成的，把 80% 精力砸在执行器 + 存储层对接上。**

## 二、技术方案：基于 DataFusion 构建

### 2.1 架构分层

```
┌──────────────────────────────────────────────────────────┐
│                    SQL 用户接口                           │
├──────────────────────────────────────────────────────────┤
│  DataFusion SQL 层（直接复用，零自研）                    │
│  ┌───────────────────────────────────────────────────┐   │
│  │  Parser (sqlparser-rs) → AST → LogicalPlan       │   │
│  │  Optimizer (RBO + 统计信息 + CBO)                 │   │
│  │  PhysicalPlan 生成                                │   │
│  └───────────────────────────────────────────────────┘   │
├──────────────────────────────────────────────────────────┤
│  EngramDB 扩展层（我们的工作重点）                        │
│  ┌─────────────────┐  ┌──────────────────────────────┐  │
│  │ TableProvider   │  │ 自定义物理算子                │  │
│  │ (存储层对接)    │  │ - IndexScan (跳表/位图/布隆)  │  │
│  │                 │  │ - VectorIndexScan (HNSW)     │  │
│  │ • 谓词下推      │  │ - DeltaAwareScan (增量感知)  │  │
│  │ • 投影下推      │  │ - CompressedAgg (压缩态聚合) │  │
│  │ • 限制下推      │  └──────────────────────────────┘  │
│  │ • 索引选择      │  ┌──────────────────────────────┐  │
│  │ • 统计信息上报  │  │ 自定义优化规则                │  │
│  └─────────────────┘  │ - 索引选择优化               │  │
│                       │ - 位图索引下推               │  │
│                       │ - 布隆过滤器下推             │  │
│                       └──────────────────────────────┘  │
├──────────────────────────────────────────────────────────┤
│  EngramDB 存储引擎（已有）                                │
│  列存 + 分类型压缩 + 多维度索引 + MVCC + WAL             │
└──────────────────────────────────────────────────────────┘
```

### 2.2 为什么选 DataFusion？

| 优势 | 说明 |
|------|------|
| **Apache 顶级项目** | 生产级质量，社区活跃（Arrow 生态核心） |
| **Rust 原生** | 与 EngramDB 技术栈完全一致，零 FFI 开销 |
| **高度可扩展** | TableProvider / PhysicalExpr / OptimizerRule 等 trait 均可自定义 |
| **向量化执行** | 基于 Arrow 的向量化执行引擎，性能优秀 |
| **SQL 覆盖完整** | 支持标准 SQL + 扩展方言，JOIN/子查询/CTE/窗口函数全有 |
| **生态丰富** | DataFusion-contrib 有大量现成扩展（json/parquet/avro 等） |
| **嵌入式友好** | 库模式使用，无服务端依赖，单文件编译即可 |

### 2.3 编译体积控制

DataFusion 依赖较多，需通过 feature flag 控制体积：

```toml
[dependencies]
datafusion = { version = "42", default-features = false, features = [
    "sql",           # SQL 解析和规划
    "unicode_expressions",  # 字符串函数
] }
# 不需要的 feature 全部关掉:
# - avro / json / parquet 等外部格式（EngramDB 自己的格式）
# - jit（编译体积太大，后期再加）
# - pyarrow / python（不需要 Python 绑定）
```

**预估二进制体积增量：5-10 MB**（纯 Rust 编译，可接受）

## 三、执行器重点优化方向

既然解析器和优化器用现成的，**执行器就是我们的主战场**。以下是 8 个重点优化方向：

### 方向 1：压缩感知扫描（Compression-Aware Scan）

**核心思想**：数据不全部解压，尽量在压缩态上直接计算。

```
传统方式:  压缩块 → 完整解压 → 扫描过滤 → 结果
EngramDB:  压缩块 → 部分解压(只需的列) → 向量化过滤 → 结果
                    ↑
              只解压需要的列 + 跳过整块（粗粒度索引）
```

- 列存天然支持列裁剪（只需扫描的列才解压）
- 稀疏主索引跳过不满足条件的整个数据块
- **进阶**：在压缩态直接做聚合（如 RLE 编码的 COUNT/SUM 可直接算）

### 方向 2：索引下推（Index Pushdown）

**核心思想**：把过滤条件尽量下推到存储层，用索引减少扫描量。

| 索引类型 | 下推场景 | 效果 |
|----------|---------|------|
| 跳表索引 | 等值查询、范围查询 | 点查 O(log n)，范围扫描大幅减少 |
| 位图索引 | 低基数列 AND/OR 组合过滤 | 基数 100 以内时，组合过滤几微秒 |
| 布隆过滤器 | 等值存在性判断 | 先过滤掉 99% 不匹配的块，再精确匹配 |

**实现方式**：自定义 OptimizerRule，在优化阶段把谓词转成索引扫描算子。

### 方向 3：向量化表达式深度优化

**核心思想**：表达式计算是 CPU 密集型，要榨干单核性能。

- 向量化执行（已有的 Vector 基础上完善）
- 分支消除（用位运算替代 if-else）
- 常量折叠 + 预计算
- **SIMD 加速**（后期，std::simd 稳定后）
- 选择向量（Selection Vector）优化过滤

### 方向 4：Delta 感知查询（Delta-Aware Query）

**核心思想**：利用 LSM 架构特性，主存储 + Delta 层合并查询。

```
查询流程:
  1. 扫描主存储（列存压缩，大批量）
  2. 扫描 Delta 层（行存，小批量）
  3. MVCC 可见性判断 → 合并结果
  4. 返回
```

优化点：
- Delta 层小，用 BTreeMap 直接扫很快
- 合并时用位图标记被删除/更新的行
- 定期合并 Delta 到主存储（Compaction）

### 方向 5：位图加速聚合

**核心思想**：低基数列的 GROUP BY 用位图索引直接算。

```sql
SELECT category, COUNT(*) FROM t GROUP BY category
```

传统方式：扫描全表 → 哈希分组 → 计数
位图方式：直接读每个 category 的位图 → 统计位数 → 结果

**性能提升：10-100 倍**（低基数场景）

### 方向 6：向量相似度查询算子

**核心思想**：HNSW 向量索引直接作为物理算子，支持 ANN 查询。

```sql
SELECT * FROM items ORDER BY embedding <-> query_vector LIMIT 10
```

- 自定义 PhysicalOperator: VectorIndexScan
- 利用 HNSW 索引做近似最近邻搜索
- 支持 L2 / 内积 / 余弦距离
- 与其他算子（Filter/Projection）串联

### 方向 7：自适应批大小（Adaptive Batch Size）

**核心思想**：根据算子类型和数据特性，动态调整批大小。

- 扫描算子：大批次（1024-4096 行），提高吞吐
- 过滤后数据少：小批次（64-256 行），减少浪费
- 聚合算子：中等批次，平衡哈希表开销和吞吐

### 方向 8：向量化 Join 优化

**核心思想**：利用列存特性优化 Hash Join。

- 哈希表向量化构建（批量插入）
- 向量化探测（批量查找）
- 字符串列用字典编码后再做 Join（整数哈希更快）
- **布隆过滤器 Join 下推**：把 Build 侧的布隆过滤器下推到 Probe 侧的扫描算子，提前过滤

## 四、实施路线（调整后）

### Phase 1：DataFusion 集成 + 基础打通（v0.8.0）

**目标**：跑通 SQL → DataFusion → EngramDB 存储的完整链路

1. **集成 DataFusion**
   - 引入 datafusion 依赖（最小 feature 集）
   - 实现 CatalogProvider（表元数据对接）
   - 实现 TableProvider（存储层对接）

2. **基础 TableProvider**
   - TableScan：列裁剪 + 全量扫描
   - 支持基本数据类型（Int64/Float64/Utf8/Boolean）
   - 统计信息上报（行数、列级别 min/max）

3. **基础谓词下推**
   - 把 Filter 表达式转成存储层可理解的谓词
   - 利用稀疏主索引跳过数据块
   - 利用布隆过滤器（等值条件）

4. **DML 支持**
   - INSERT（写入 Delta 层）
   - UPDATE / DELETE（通过 DataFusion 的 TableUpdate 接口）

5. **验证**
   - 跑通 TPC-H Q1（简单聚合）
   - 跑通 TPC-H Q6（过滤 + 聚合）

### Phase 2：索引下推 + 性能优化（v0.8.x）

**目标**：把 EngramDB 的索引能力全部暴露给查询引擎

1. **跳表索引下推**
   - 自定义 OptimizerRule：Filter + TableScan → IndexScan
   - 支持等值查询和范围查询
   - 索引选择代价估算

2. **位图索引下推**
   - BitmapIndexScan 物理算子
   - 多列位图 AND/OR 组合
   - 低基数列自动选择位图索引

3. **布隆过滤器下推**
   - Join 时布隆过滤器下推到扫描层
   - 等值查询先用布隆过滤再精确匹配

4. **向量化优化**
   - 表达式向量化（算术/比较/逻辑）
   - 过滤向量化（选择向量）
   - 聚合向量化（哈希聚合优化）

### Phase 3：高级算子 + 深度优化（v0.9.x）

**目标**：补齐高级算子，性能达到 DuckDB 同级

1. **Hash Join 优化**
   - 向量化 Hash Join
   - 布隆过滤器 Join 下推
   - 字典编码加速字符串 Join

2. **窗口函数**
   - 基于 DataFusion 窗口函数框架
   - 优化排序（TopN 优化）
   - 排名函数 / 分析函数 / 窗口聚合

3. **向量相似度查询**
   - VectorIndexScan 算子
   - HNSW 索引对接
   - 距离函数（L2 / 内积 / 余弦）

4. **压缩态计算**
   - RLE 编码列直接聚合
   - Delta 编码列的 SUM/COUNT 优化
   - 位图索引直接算 GROUP BY

### Phase 4：生产级完善（v0.10.x+）

1. **统计信息收集**
   - ANALYZE TABLE
   - 直方图
   - NDV（唯一值数）估算

2. **并发控制**
   - 多查询并发执行
   - 资源隔离
   - 查询取消

3. **物化视图**
   - 基于 DataFusion 的视图机制
   - 增量刷新
   - 查询重写

## 五、工作量对比

| 方案 | 解析器 | 优化器 | 执行器 | 总工作量 |
|------|--------|--------|--------|----------|
| 全自研 | 大（3-6月） | 很大（6-12月） | 中（3-6月） | **12-24 月** |
| **DataFusion + 自研执行器** | **零** | **小（1-2月，自定义规则）** | 中（3-6月） | **4-8 月** |

**节省约 2/3 的工作量**，而且质量更有保障。

## 六、对现有代码的影响

### 保留的模块
- ✅ 存储引擎全部（column_store / compression / index / wal / txn）
- ✅ Vector 向量化基础
- ✅ 数据类型系统

### 替换的模块
- 🔄 SQL 解析器 → DataFusion SQL Parser

### 改造的模块
- 🔧 执行算子 → 适配 DataFusion ExecutionPlan trait

- 🔧 表元数据 → 实现 CatalogProvider / TableProvider

- ➕ datafusion_ext/（DataFusion 扩展层）
  - table_provider.rs
  - catalog.rs
  - optimizer_rules/
