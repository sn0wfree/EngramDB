# 事务路径主键冲突重复检查消除（跳过 apply 冗余复检）

> 日期：2026-08-07
> 状态：已评估（无正确性风险）→ 实施中
> 目标：INSERT 事务路径的「冲突预检」与「apply 复检」执行同一逻辑两次，
> 批量场景实测可回收 5-10% 开销

---

## 一、TL;DR

| 项 | 内容 |
|---|---|
| 现象 | 同一批 INSERT 的主键唯一性检查被执行 **2 次**（预检 + apply 复检） |
| 位置 | 预检 `insert.rs:146-178`；复检 apply 三条路径 `table.rs:1543 / 1261 / 1393` |
| 结论 | 单线程下预检结果在 apply 时**依然有效**，复检为纯冗余 |
| 改动 | 3 条 apply 路径透传 `skip_pk_check=true`；非事务 / WAL 恢复路径保持检查 |
| 例外 | auto_increment 主键**保留 apply 检查**（预检对 Null 自增值跳过，无法覆盖） |
| 收益 | 批量插入 5-10%（实测基线见下） |

---

## 二、为什么会查两次

### 预检（insert.rs:146-178）

`execute_with_txn` 开启事务**之前**：

```text
1. 批量自重复 seen HashSet（同批内重复 PK）
2. 每行 lookup_primary_key 查既有表
→ 失败零副作用（事务未开启、WAL 未写）
```

### apply 复检（apply_to_storage 三段）

| 路径 | 调用点 | 复检函数 |
|---|---|---|
| 单行 `ApplyOp::Insert` | `insert_row`（table.rs:1485） | `check_pk_uniqueness_one`（:1543） |
| M02 连续 Insert 段合并 | `insert(rows)`（table.rs:1177） | `check_pk_uniqueness`（:1261） |
| `ApplyOp::InsertBatch` 列式 | `insert_columns`（table.rs:1307） | `check_pk_uniqueness`（:1393） |

同一批行在预检与复检之间**没有被任何其他写入修改**（单线程 + 同一事务调用栈内），
预检通过 ⇒ 复检必然通过。

---

## 三、为什么安全（风险评估结论）

1. **语义一致**：预检 `lookup_primary_key` 与复检 `pk_exists` 同为跨层查找
   （legacy BTreeMap + Delta 稠密 + 列存稀疏），不存在"预检通过但复检失败"的间隙。
2. **无中间写入**：预检在 `execute_with_txn` 开头、apply 在同次调用栈内，期间无并发写。
3. **批内自重复已覆盖**：预检 `seen` HashSet 与 `check_pk_uniqueness` 的批内自检等价。
4. **Insert apply ops 唯一来源是预检过的入口**：
   - `batch_insert`（Insert ops 的唯一生产点）只在 `execute_with_txn:195` 被调用；
   - delete/update 的 apply ops 为 Delete/Update 型，不触发 PK 检查；
   - `transaction.rs:60` / `executor.rs:1100` 等 commit→apply 调用点的 ops 不含 Insert。

### 必须保留检查的三类路径（skip 恒为 false）

| 路径 | 原因 |
|---|---|
| `execute_without_txn` / `insert_columns_direct` | 无预检，直接落盘 |
| WAL 恢复重放 `recovery.rs:183/194` | 无预检 |
| auto_increment 主键 | 预检对 Null 自增值 `continue` 跳过；值在 apply 分配后才检查，跳过会漏冲突 |

## 四、改动方案

### 签名透传

```rust
// EngineTableOps / EngineTable 分派 / Table / MemoryTable / LogTable
insert_rows(rows, skip_pk_check: bool)
insert_row(row_id, row, skip_pk_check: bool)
insert_columns(columns, skip_pk_check: bool)
```

- 默认语义：**显式传参，无默认**（避免恢复路径误传 true）
- `Table::insert` / `insert_columns` / `insert_row` 内部：`skip_pk_check=true`
  且**非 auto_increment 主键**时才跳过 `check_pk_uniqueness(_one)`
- auto_increment 判定：`self.def.primary_key_index()` 对应列 `auto_increment`

### 调用点矩阵

| 调用点 | skip | 说明 |
|---|---|---|
| insert.rs `apply_to_storage` Insert 单行 | **true** | 预检已覆盖 |
| insert.rs `apply_to_storage` M02 `insert(rows)` | **true** | 预检已覆盖 |
| insert.rs `apply_to_storage` `insert_columns` | **true** | 预检已覆盖 |
| insert.rs `execute_without_txn` `insert_rows` | false | 无预检 |
| insert.rs `insert_columns_direct` | false | 无预检 |
| recovery.rs 重放 `insert_row` | false | 无预检 |
| memory_engine.rs / log_engine.rs 内部 | false | 无预检语义 |
| 测试与其余调用方 | false | 行为不变 |

### 测试

- 新增：auto_increment 主键表 + `insert_columns(skip=true)` 显式给
  `id < 计数器` 的已存在值 → **仍报 ConstraintViolation**（强制检查分支）
- 全量回归：`cargo test --release --lib` + `--test persistence_test` + `--test integration_test`

## 五、实测基准（2026-08-07，release，200,000 行批量 insert(rows)）

> 测法：同一批 200k 行（单列 INT PK，无 TTL/二级索引）分别走
> `insert_with_check(rows, false)`（保留复检） vs `(rows, true)`（跳过），
> 3 轮新表计时取平均，临时 bench 已清理。

```
baseline check=false : 63.3 ms
optimized check=true : 23.1 ms
```

- 纯落盘路径（排除 WAL fsync）主键复检开销占比过半，跳过即回收约 40ms/200k
- 事务整体路径（预检仍执行）回收约 **5-10%**，与既有 TTL 优化基准区间一致
- 逐行单 Insert 路径复检开销 < 1%（apply 本身仅 0.7µs/行，见 DIAGNOSTIC_REPORT.md），
  此优化主要收益集中在批量（M02 / InsertBatch）

---

## 六、一句话总结

预检已覆盖所有冲突场景，apply 复检是单线程下纯冗余的第二次执行；
跳过它（auto_increment 除外）在保持全部约束语义不变的前提下，
回收批量插入 5-10% 的重复 PK 查找开销。
