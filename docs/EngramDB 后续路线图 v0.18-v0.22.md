## 一、现状校准

### 1.1 为什么从 v0.18 开始

原路线图按 v0.14 → v0.15 → v0.16 → v0.17 → v0.18 顺序规划，但实际开发是并行推进的——很多规划在后续版本的功能已经合入 main 分支，版本号一直停在 0.14.0 没动。

**已在代码中的「未来功能」清单**：

| v0.15 | 混合搜索 | — | — | ✅ 已实现 |

**结论**：版本号已统一升至 v0.18.0 作为阶段性标记。路线图从 v0.18 的剩余性能优化开始，向后规划。

## 三、各版本详细规划

### v0.18 — 性能攻坚（进行中）

**主题**：把已有的功能跑快，消除明显的性能瓶颈

**目标**：核心查询路径性能提升 2~5x，逼近 DuckDB 同量级

| 编号 | 功能点 | 优先级 | 工作量 | 状态 | 说明 |
|------|--------|--------|--------|------|------|
| P0-1 | ColumnData::slice 替代 take_front | P0 | 0.5 天 | ✅ 完成 | 消除扫描分块 O(N²/B) drain 开销 |
| P0-2 | Varchar offset+data 双数组 | P0 | 3~5 天 | ⏳ 待做 | 涉及面广（367 处引用），需谨慎重构 |
| P0-3 | 类型化表达式快速路径接入 | P0 | 1 天 | ✅ 完成 | 数值列二元运算零 Value 构造 |
| P1-1 | 类型化分组聚合 | P1 | 3 天 | ✅ 完成 | 键+值双类型化，热路径零 Value |
| P1-2 | LEFT/RIGHT JOIN 类型化键 | P1 | 2 天 | ⏳ 待做 | Hash Join 外连接场景加速 |
| P1-3 | bumpalo arena 分配器 | P1 | 3~4 天 | ⏳ 待做 | 执行期内存分配优化，减少 malloc/free |
| P2-1 | WAL checkpoint 临时修复 | P2 | 0.5 天 | ✅ 完成 | 移除错误 truncate，v0.19 彻底解决 |
| P2-2 | 基准测试套件完善 | P2 | 2 天 | ⏳ 待做 | 统一 bench 框架，可复现性能报告 |

**里程碑**：所有 P0 + P1 完成，核心查询 TPC-H 风格基准测试有量化结果

## 四、关键决策点

在推进过程中，以下决策点需要提前对齐：

| 决策点 | 影响版本 | 选项 | 建议 |
|--------|---------|------|------|
| **GraphEngine 技术路线** | v0.19 | A. 自研轻量邻接表（基于列存）<br>B. 集成现有图库（Kuzu/Ladybug） | A 起步，保持单文件优势；v0.21 后评估是否需要深度集成 |
| **全文检索分词方案** | v0.20 | A. 简单空格/规则分词<br>B. 集成 jieba/分词库 | A 起步（英文场景够用），中文分词后续加 feature flag |
| **MCP 服务器时机** | v0.22 | A. v0.22 就做<br>B. 等 Python 绑定稳定后再做 | B 更稳妥——Python 生态成熟后 MCP 自然跟上 |
| **与 Cognee 的关系** | 全程 | A. 竞争替代<br>B. 互补（做底层存储） | B——EngramDB 是基础设施层，Cognee 是应用层，可做 Cognee 后端适配器 |
| **单文件 vs 性能的取舍** | v0.19+ | A. 严格单文件（WAL 段在同一文件内分区）<br>B. 允许 WAL 独立文件 | A 优先——单文件是核心卖点，WAL 段用文件内区域划分实现 |

## 五、风险与应对

| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|---------|
| 图引擎实现复杂度超预期 | 中 | 高 | v0.19 先做最简可用版（邻接表 + BFS），不追求一步到位 |
| 性能优化收益不及预期 | 中 | 中 | 每项优化先做微基准验证，收益不明显就回退，不恋战 |
| WAL 段滚动引入数据一致性 bug | 低 | 极高 | 充分的 property-based test + 故障注入测试 |
| 单人开发节奏不可持续 | 中 | 高 | 聚焦核心路径，非核心功能接受「能用就行」，社区贡献补全 |
| Cognee Rust 重写后直接竞争 | 低 | 中 | 保持差异化：单文件 + SQL + 事务 + 多引擎，不跟 Cognee 比应用层功能 |
