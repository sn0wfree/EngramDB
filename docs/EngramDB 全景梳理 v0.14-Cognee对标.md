> 梳理日期：2026-10-21
> 当前版本：v0.14.0（SQL 基础补齐阶段）

## 一、项目定位

### 1.1 一句话定位

**面向 AI Agent 场景的嵌入式多引擎单文件数据库。**

- **嵌入式**：作为库链接到应用进程，零配置、无后台进程
- **单文件**：所有持久化数据在一个文件里（类比 SQLite）
- **多引擎**：同一数据库内支持多种存储引擎，不同表选不同引擎（列存/内存/日志/图）
- **AI Agent 原生**：从设计上适配 Agent 的多种工作负载

### 1.2 差异化定位

| 维度 | EngramDB | Cognee | SQLite | DuckDB |
|---|---|---|---|---|
| **层级** | 基础设施层（数据库） | 应用层（记忆平台） | 基础设施层 | 基础设施层 |
| **核心能力** | 多引擎 + SQL + 事务 + 单文件 + 向量 | 知识图谱 + 记忆演化 + 混合检索 | 行存 + 事务 + SQL | 列存 + 分析 + SQL |
| **部署** | Rust 嵌入式库（零依赖） | Python 库 / Docker / Cloud | C 库（零依赖） | C++ 库 |
| **Agent 适配** | 内核级（向量/TTL/缓存/限流） | 应用级（完整记忆平台） | 无（通用数据库） | 无（分析数据库） |
| **单文件** | ✅ 真正单文件 | ❌ 三文件（SQLite+LanceDB+Ladybug） | ✅ | ❌（多文件） |

**关键洞察**：EngramDB 与 Cognee 是**互补而非竞争**关系。Cognee 是应用层记忆平台，EngramDB 是基础设施层数据库。EngramDB 甚至可以作为 Cognee 的底层存储引擎——用单文件替代三套独立存储，在嵌入式/端侧场景下优势明显。

## 四、Cognee 对标：10 个可借鉴点

### 高优先级（⭐⭐⭐⭐⭐）

#### 1. 图引擎作为第四存储引擎
- **现状**：只有列存、内存、日志三个引擎，图能力完全缺失
- **价值**：Agent 记忆检索核心是关系推理，纯向量不够。与 HNSW 向量索引形成互补
- **落地**：M6 GraphEngine，图节点带向量支持混合检索，SQL 扩展（GRAPH TRAVERSE）
- **版本建议**：v0.19（多引擎架构完成后）

#### 2. DataPoint 统一数据模型 + 溯源链
- **现状**：行是基本单元，无统一数据模型，溯源能力缺失
- **价值**：Agent 场景记忆可追溯是刚需，为图引擎/文档树索引打基础
- **落地**：v0.15 文档摄入 API 引入 IngestedDocument 模型 → v0.16 扩展为通用 DataPoint
- **版本建议**：v0.15 起步

#### 3. 记忆自进化机制（memify）
- **现状**：路线图仅规划了"记忆重要性评分+衰减"，定位偏 TTL 扩展
- **价值**：Agent 数据库与普通数据库的核心差异点。记忆不是静态存储，随使用演化
- **落地**：v0.17 升级为完整记忆优化引擎（MEMIFY SQL 扩展），含重要性评分/衰减/关联发现/合并摘要
- **版本建议**：v0.17

### 中优先级（⭐⭐⭐⭐）

#### 4. 分层检索体系（14 种模式）
- **现状**：只有基础向量 Top-K + 标量过滤（规划中）
- **价值**：不同查询类型走不同路径，渐进式实现
- **落地**：v0.15（3 种基础）→ v0.16（+2 种混合）→ v0.17+（+图相关）
- **版本建议**：v0.15 起步

#### 5. ECL 管线架构的插件化设计
- **现状**：规划了"插件化摄取管线"（Ag13），分四级插件
- **价值**：Task + Pipeline 抽象更通用，不仅用于摄入，也可用于 ETL/索引构建
- **落地**：v0.16 Ag13 实现时采用 Task/Pipeline 抽象
- **版本建议**：v0.16

#### 6. Session 级短期记忆
- **现状**：MemoryEngine 规划用于临时状态，无专门 Session 抽象
- **价值**：Agent 对话上下文是典型短期记忆，有特殊访问模式
- **落地**：v0.17 在分层记忆接口中增加 Session 层
- **版本建议**：v0.17

#### 7. Schema/Dataset 级组织与权限
- **现状**：表是基本组织单元，无命名空间级组织
- **价值**：Agent 应用需管理多个项目/用户的记忆，逻辑分组便于备份迁移
- **落地**：v0.16 引入 Schema 支持（CREATE SCHEMA、schema.table 语法）
- **版本建议**：v0.16

### 低优先级（⭐⭐⭐）

| # | 借鉴点 | 优先级 | 落地版本 |
|---|---|---|---|
| 8 | 本体（Ontology）支持 | ⭐⭐⭐ | v0.21+ |
| 9 | MCP 服务器作为标准接口 | ⭐⭐⭐ | v0.20+ |
| 10 | 自适应检索（Trace Optimization） | ⭐⭐ | 长期研究方向 |

## 七、核心问题与风险

| 问题 | 影响 | 建议 |
|---|---|---|
| 功能完成度低（~20%） | 无法支撑复杂 Agent 场景 | 聚焦 Agent 刚需，优先做 v0.15 Agent 差异化 |
| 性能优化验证困难（沙箱 2 核） | 优化效果无法量化 | 本地基准测试 + CI 自动化 |
| 图引擎实现复杂度高 | 可能拖慢整体进度 | 先做轻量版（列存+邻接表），再深化 |
| 单文件 vs 多引擎的平衡 | 多引擎共享单文件增加复杂度 | 严格的 PageAllocator + 引擎独立分区 |
| Cognee 正在 Rust 重写 | 未来可能直接竞争 | 聚焦差异化：单文件 + SQL + 事务 + 多引擎 |
