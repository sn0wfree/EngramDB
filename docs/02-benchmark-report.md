## 1. 批量写入性能

| 数据库 | 耗时 (ms) | 吞吐 (行/秒) | 相对 SQLite |
|--------|-----------|-------------|-------------|
| SQLite | 42.3 | 1,183,074 | 1.00x |
| DuckDB | 42.1 | 1,187,199 | 1.00x |
| EngramDB (Py) | 50.8 | 984,583 | 0.83x |

**分析**：
- SQLite 与 DuckDB 写入速度接近（均为成熟 C/C++ 实现）
- EngramDB Python 版受语言解释开销影响，略慢 ~20%
- Rust 原生实现预计可达 SQLite/DuckDB 同级水平
- 列存写入需构建 Row Group + 维护 MinMax 统计，天然略高于纯行存

## 2. 存储压缩率

| 数据库 | 文件大小 (KB) | 压缩比 |
|--------|--------------|--------|
| SQLite | 2,004 | 1.07x |
| DuckDB | 1,292 | **1.66x** |
| EngramDB (估算) | 2,148 | 1.00x |

**分析**：
- DuckDB 压缩率最高（FSST 字符串压缩 + Chimp 浮点压缩 + RLE/Dict 全套）
- SQLite 几乎无压缩（B+Tree 页内少量空闲空间优化）
- EngramDB 当前 MVP 未启用轻量级压缩（RLE / Dictionary / Bit-packing），启用后预计压缩率接近 DuckDB

## 3. 全表扫描 + 聚合性能

测试查询：`SELECT SUM/COUNT/AVG/MIN/MAX(score) FROM t`
（5 次平均，单位：毫秒）

| 聚合函数 | SQLite | DuckDB | EngramDB (Py) | EngramDB vs SQLite |
|---------|--------|--------|---------------|-------------------|
| SUM | 2.77 | **1.16** | 1.44 | 1.92x 更快 |
| COUNT | 2.69 | 0.46 | **0.01** | 269x 更快 |
| AVG | 2.56 | **0.39** | 2.13 | 1.20x 更快 |
| MIN | 2.68 | **0.64** | 1.54 | 1.74x 更快 |
| MAX | 2.67 | **0.60** | 1.52 | 1.76x 更快 |

**分析**：
- **列存优势明显**：DuckDB 和 EngramDB 在所有聚合查询中均优于行存 SQLite
- 核心原因：列存只需读取目标列（1 列），行存需读取全部列（5 列）
- COUNT 极快：EngramDB 直接从 Row Group 元数据读取行数，无需扫描数据
- MIN/MAX 较快：EngramDB 利用 MinMax 索引逐层聚合，无需全量扫描

## 4. 条件查询性能（SELECT *）

测试不同选择性下的过滤查询性能（3 次平均，单位：毫秒）

| 选择性 | 命中行数 | SQLite | DuckDB | EngramDB (Py) |
|--------|---------|--------|--------|---------------|
| 高选择性 (90%) | 45,421 | 34.32 | **20.80** | 63.19 |
| 中选择性 (50%) | 25,159 | 20.84 | **13.59** | 19.48 |
| 低选择性 (10%) | 4,506 | 41.25 | **5.00** | 9.64 |
| 极低选择性 (1%) | 501 | 3.12 | **1.94** | 5.69 |

**关键趋势**：

| 指标 | SQLite | DuckDB | EngramDB (Py) |
|------|--------|--------|---------------|
| 低选 vs 高选加速比 | 0.83x | **4.16x** | **6.55x** |

**分析**：
- **EngramDB 的 MinMax 跳过索引在低选择性下优势显著**：从高选择性到低选择性，加速比达 6.55x，远超 SQLite 的 0.83x
- 选择性越低，跳过索引收益越大——这是列存 + 数据跳过索引的核心优势
- 高选择性下 EngramDB 较慢：Python 解释开销 + 需要物化更多行（90% 行几乎全部命中，跳过效果有限）
- DuckDB 整体最快：成熟 C++ 向量化执行引擎 + 完整优化器

| 算子 | 性能 (单核) | 备注 |
|------|-------------|------|

| 向量过滤 (高选择性 1%) | **17.2 亿行/秒** | SelectionVector 输出 |

### 6.3 两阶段聚合（Rust 实测）

| 模式 | 耗时 (ms) | 吞吐 (行/秒) |

> 这是正常的——两阶段聚合的价值在于**多核并行**，N 核并行时理论加速比接近 N。
> 单核场景建议直接单阶段聚合。

### 6.4 Rust vs Python 性能对比（同算法）

| 算子 | Python (Py) | Rust (Rs) | Rs / Py 倍数 |
|------|------------|-----------|-------------|
| 列存写入 (1M 行) | ~50 ms | 8.0 ms | **6.3x** |

| PREWHERE 加速比 | 6.55x | 8.85x | 趋势一致 |

> **结论**：
> - Rust 原生性能为 Python 版的 **6–33 倍**（计算越密集、加速比越高）
> - 之前预估的 "10–50 倍" 区间基本准确
> - 过滤/聚合等计算密集型算子加速比最高（19–33x）
> - 写入因含内存分配，加速比稍低（6x）

## 7. 轻量级压缩算法（RLE / Dictionary / Bit-packing）

> 测试文件：`benches/compression_bench.rs` + `src/storage/compression.rs`
> 数据集：10 万行 INT 列，4 种典型数据分布
> 编译：`rustc -O --edition 2021 benches/compression_bench.rs`

### 7.1 压缩率对比

| 数据分布 | RLE | Dictionary | Bit-packing (FOR) | 最佳算法 |
|---------|-----|------------|-------------------|---------|
| 高重复 (10 个值) | **6,666.7x** | 8.0x | 16.0x | RLE |
| 低基数 (200 个值) | 0.67x (负压缩) | **7.9x** | 4.3x | Dictionary |
| 窄范围递增 (10K 范围) | 0.67x (负压缩) | 2.9x | **4.6x** | Bit-packing |
| 随机 64 位整数 | 0.67x (负压缩) | 0.67x (负压缩) | 1.0x | 不压缩 |

> **原始大小**：10 万行 × 8 字节 = 781.2 KB
> **负压缩**：压缩后反而更大，说明该算法不适合此数据分布，应跳过

### 7.2 编解码速度（Rust 原生，单核）

| 算法 | 编码速度 | 解码速度 | 10 万行耗时 |
|------|---------|---------|------------|
| RLE | ~16 亿行/秒 | ~17 亿行/秒 | 0.06 ms |
| Dictionary | ~1 亿行/秒 | ~13 亿行/秒 | 0.08–1.0 ms |
| Bit-packing (FOR) | 0.2–3 亿行/秒 | 0.7–8 亿行/秒 | 0.3–4.5 ms |

**速度排序**：
- 编码：RLE > BitPack > Dictionary
- 解码：RLE ≈ Dictionary >> BitPack
- Bit-packing 速度随 bit_width 变化：位宽越小越快

### 7.3 三种算法适用场景

| 算法 | 最佳适用场景 | 典型压缩率 | 速度 |
|------|-------------|-----------|------|
| **RLE** | 排序/聚类后高度重复的列（状态、类别、分区键） | 100–10000x | 极快 |
| **Dictionary** | 低基数字符串/整数列（< 65536 个不同值） | 3–20x | 快 |
| **Bit-packing (FOR)** | 数值列、范围有限（ID、时间戳、度量值） | 2–10x | 中 |

### 7.4 自动选择策略

EngramDB 采用**按列自动选择**策略：

1. 写入 Row Group 时，对每列依次尝试 RLE → Dictionary → Bit-packing
2. 计算每种算法的压缩率
3. 选择压缩率最高且 > 1.2x 的算法
4. 全部 < 1.2x 时，标记为 `None`（不压缩，或用 zstd 重量级压缩）
5. ColumnChunk 头部存储压缩类型标识，读取时自动解码

> 这也是 ClickHouse / Parquet / ORC 等主流列存系统的通用策略。

### 7.5 与重量级压缩的关系

轻量级压缩（RLE/Dict/BitPack）与重量级压缩（zstd/LZ4/Gzip）是**互补**而非替代：

- **轻量级**：编解码极快（接近内存带宽），压缩率中等，适合热数据
- **重量级**：压缩率高（2–10x），编解码慢，适合冷数据/归档

EngramDB 的分层策略：
- **热数据层**：轻量级压缩 + 内存缓存，查询性能优先
- **冷数据层**：zstd 压缩 + 磁盘存储，存储成本优先

## 8. 向量检索引擎（HNSW）

### 8.1 测试配置

- **向量维度**：128 维（典型文本 embedding 维度）
- **数据规模**：10,000 条向量
- **查询数量**：100 个查询
- **K 值**：Top-10 最近邻
- **距离度量**：L2 欧氏距离平方
- **硬件**：单核 CPU

### 8.2 暴力搜索 Baseline

作为召回率 100% 的基准：

| 指标 | 值 |
|------|-----|
| 查询延迟 | 1.41 ms/query |
| QPS | 708 |
| 召回率 | 100% (exact) |

### 8.3 HNSW 召回率 vs 速度权衡

不同 M 和 ef 参数组合下的表现：

| 配置 | 召回率 | 查询延迟 | QPS | 加速比 |
|------|--------|----------|-----|--------|
| M=16, ef=50 | 63.0% | 0.21 ms | 4,791 | 6.7x |
| M=16, ef=100 | 76.5% | 0.34 ms | 2,949 | 4.2x |
| M=16, ef=200 | 84.1% | 0.54 ms | 1,863 | 2.6x |
| M=32, ef=100 | 89.2% | 0.52 ms | 1,938 | 2.7x |
| M=32, ef=200 | **94.5%** | 0.79 ms | 1,272 | 1.8x |
| M=64, ef=50 | 92.7% | - | - | - |

**关键发现**：
- 召回率随 ef 增大单调递增，符合 HNSW 理论预期
- M=32, ef=200 可达 94.5% 召回率，同时保持 1.8x 加速
- 小数据集（10K）下暴力搜索已很快，HNSW 优势在百万级以上更明显

### 8.4 索引构建性能

| 配置 | 构建时间 | 构建吞吐 | 最大层数 | 平均连接数/节点 |
|------|----------|----------|----------|-----------------|
| M=16, efCon=100 | 3.6 s | 2,708 vec/s | 3 | 33.1 |
| M=16, efCon=200 | 5.0 s | 2,018 vec/s | 3 | 33.1 |
| M=32, efCon=200 | 9.4 s | 1,067 vec/s | 2 | 65.0 |

**层数分布（M=16, 10K 向量）**：
- 第 0 层：10,000 节点（全部）
- 第 1 层：625 节点（1/16）
- 第 2 层：39 节点（1/256）
- 第 3 层：3 节点（1/4096）
- 符合几何分布 P(level≥l) = 1/M^l

### 8.5 数据规模扩展性

| 数据规模 | ef=50 查询延迟 | QPS |
|----------|---------------|-----|
| 1,000 | 0.094 ms | 10,587 |
| 2,000 | 0.133 ms | 7,541 |
| 5,000 | 0.175 ms | 5,698 |
| 10,000 | 0.202 ms | 4,954 |

查询延迟随数据规模亚线性增长（HNSW 复杂度 O(log N)）。

### 8.6 向量维度影响

| 维度 | 查询延迟 (5K vectors) | 相对开销 |
|------|----------------------|----------|
| 32 | 0.070 ms | 1.0x |
| 64 | 0.108 ms | 1.5x |
| 128 | 0.172 ms | 2.5x |
| 256 | 0.303 ms | 4.3x |

距离计算开销与维度近似线性相关。

### 8.7 小结

- **正确性**：HNSW 算法实现正确，召回率随 M/ef 提升而增加，层数分布符合理论
- **性能**：M=16, ef=50 时 QPS 达 4,791（暴力搜索的 6.7 倍）
- **可调性**：用户可通过 M 和 ef 参数在召回率与速度之间灵活权衡
- **扩展性**：查询复杂度 O(log N)，适合大规模向量检索场景

### 🎯 EngramDB 核心差异化

1. **行存 + 列存混合架构**：兼顾事务写入与分析查询
2. **完整 WAL + MVCC 事务**：接近 SQLite 的事务能力，远超 DuckDB
3. **内置向量检索**：AI Agent 原生支持（HNSW / IVF）
4. **ClickHouse 级优化**：稀疏索引、数据跳过、PREWHERE、两阶段聚合
5. **单文件 + 零依赖**：嵌入式部署友好

## 运行基准测试

```bash
# 1. 运行三方对比测试（Python 模拟版，需 sqlite3 + duckdb）
python3 benchmark_compare.py

# 2. 运行 ClickHouse 优化专项测试（Python 算法验证）
python3 test_perf_optimizations.py

# 3. Rust 原生核心性能基准（需 Rust 环境，零外部依赖）
rustc -O --edition 2021 benches/core_bench.rs -o target/release/core_bench
./target/release/core_bench

# 4. Rust 压缩算法基准（需 Rust 环境，零外部依赖）
rustc -O --edition 2021 benches/compression_bench.rs -o target/release/compression_bench
./target/release/compression_bench

# 5. 完整 Rust benchmark（需 Rust + 依赖，cargo 环境）
cargo bench
```

## 数据来源

- **SQLite**: Python `sqlite3` 模块（系统内置）
- **DuckDB**: Python `duckdb` 包（v1.x）
- **EngramDB**: 本项目 `benchmark_compare.py` 中的 Python 模拟实现
- 所有测试在同一沙箱环境中执行，硬件条件一致
