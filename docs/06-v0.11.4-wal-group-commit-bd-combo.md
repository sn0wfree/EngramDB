# v0.11.4 — WAL 组提交加速 + B+D 组合方案

## 版本概述

v0.11.4 围绕「AI Agent 日常交互存储」场景，落地两项关键优化：

1. **WAL 组提交加速** — Sync 模式下多条事务共享一次 fsync，写入吞吐提升 5~20x，同时保持「已 fsync 数据绝对不丢」的持久化保证
2. **B + D 组合方案** — Delta 聚簇（方案B）+ 覆盖索引（方案D）叠加，针对 session_id 查询场景实现双重加速

> 设计决策：用户明确拒绝「纯内存写入」（单文件数据库无后台进程，数据丢失风险过高），改用 WAL 组提交作为加速手段。

## 一、WAL 组提交（Group Commit）

### 核心机制

传统 Sync 模式：每次 commit → flush → fsync，fsync 是性能瓶颈（毫秒级）。

组提交模式：每次 commit → flush（到 page cache）→ 计数，累计达到 `group_commit_size` 或 `group_commit_max_bytes` 时才做一次 fsync。

```
Txn1 commit ──┐
Txn2 commit ──┤
Txn3 commit ──┼──→ 一次 fsync（共享）
Txn4 commit ──┘
```

### 配置参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `wal_group_commit_size` | usize | 0（禁用） | 每 N 次 commit 做一次 fsync |
| `wal_group_commit_max_bytes` | usize | 65536（64KB） | 缓冲区达到 N 字节时强制 fsync |

两个条件是「或」关系，任一满足即触发 fsync。

### 性能影响

- **吞吐提升**：5~20x（取决于 group size 和写入大小）
- **延迟影响**：单条 commit 延迟从 ms 级降至 μs 级（跳过 fsync）
- **持久化保证**：已 fsync 的数据 100% 不丢；未 fsync 的最多丢 `group_commit_size` 条

### 风险控制

- `sync_wal()` 可在关键节点强制刷盘（如用户点击保存、会话结束时）
- 进程崩溃（非 OS 崩溃）时，page cache 中的数据仍在，重启后 WAL 可恢复
- 推荐配置：`group_commit_size = 8~32`，平衡吞吐与风险

### API

```rust
// 开启组提交（每 16 次 commit 共享一次 fsync）
conn.set_wal_group_commit_size(16);

// 关键节点强制刷盘
conn.sync_wal().unwrap();
```

## 二、方案B：Delta 聚簇（Clustering）

### 核心机制

Compact 时按聚簇列（如 `session_id`）的值分组，相同 key 的行物理上连续写入列存。

```
无聚簇：[msg1 sessA] [msg2 sessB] [msg3 sessA] [msg4 sessB]
         分散在不同数据块，查询需扫描整个表

有聚簇：[msg1 sessA] [msg3 sessA] [msg2 sessB] [msg4 sessB]
         同一会话连续存储，范围查询只需扫描少量数据块
```

### 效果

- 按聚簇列的等值查询 / 范围查询：IO 量减少 10~100x（取决于基数）
- 典型场景：AI Agent 按 `session_id` 查询整个会话的消息历史

### API

```rust
// 设置聚簇列（建表后调用，后续 compact 生效）
conn.set_cluster_key("messages", "session_id").unwrap();

// 手动触发 compact（聚簇在 compact 时生效）
conn.compact("messages").unwrap();
```

## 三、方案D：覆盖索引（Covering Index）

### 核心机制

跳表索引冗余存储高频查询列的值，查询时直接从索引返回，不需要回表查主存储。

```
普通索引：key → row_id → 回表查其他列（随机 IO）
覆盖索引：key → {row_id, col1, col2, ...} → 直接返回（顺序扫描索引）
```

### 数据结构

```rust
pub struct IndexEntry {
    pub row_id: u32,
    pub included: Vec<Value>,  // 覆盖列的值
}
```

### 效果

- 覆盖列的查询：跳过回表，性能提升 2~5x
- 典型场景：`session_id` 索引覆盖 `timestamp`、`role`，查询会话消息列表时只需扫索引

### API（底层）

```rust
// 创建带覆盖列的跳表索引
let mut idx = SkipListIndex::with_included(false, 2);  // 2 个覆盖列

// 插入时附带覆盖列的值
idx.insert_with_included(key, row_id, vec![ts_val, role_val]);

// 查询时直接获取覆盖列值
for entry in idx.range_entries(low, high) {
    let ts = &entry.included[0];
    let role = &entry.included[1];
}
```

## 四、B + D 组合方案

### 为什么叠加有效

| 优化 | 加速层级 | 适用场景 |
|------|----------|----------|
| B（聚簇） | 物理存储层 | 大范围扫描（整个会话） |
| D（覆盖索引） | 索引层 | 点查询 / 小范围查询 |

两者互补：
- **大范围查询**（取整个会话几百条消息）：聚簇效果更好，减少 IO 次数
- **小范围查询**（取最近 10 条）：覆盖索引更好，完全不需要回表
- **带过滤条件的查询**：覆盖索引快速定位 + 聚簇存储连续扫描

### AI Agent 场景推荐配置

```rust
let mut conn = Connection::open_with_config("agent.db", Config {
    // WAL 加速：组提交 16 条一批
    wal_group_commit_size: 16,
    wal_group_commit_max_bytes: 65536,
    
    // Delta 合并：自适应分桶
    compact_strategy: CompactStrategy::default_adaptive(122_880),
    
    ..Config::default()
}).unwrap();

// 建表
conn.execute("CREATE TABLE messages (
    id BIGINT PRIMARY KEY,
    session_id VARCHAR,
    timestamp BIGINT,
    role VARCHAR,
    content VARCHAR
)").unwrap();

// 方案B：按 session_id 聚簇
conn.set_cluster_key("messages", "session_id").unwrap();

// 方案D：session_id 索引覆盖 timestamp + role
// （通过底层 API 创建覆盖索引）
```

### 预期收益

| 指标 | 基线（v0.11.3） | v0.11.4（B+D+WAL） | 提升 |
|------|-----------------|---------------------|------|
| 写入吞吐（小事务） | ~1x | 5~20x | WAL 组提交 |
| 会话历史查询 | ~1x | 10~100x | 聚簇 + 覆盖索引 |
| 最近 N 条查询 | ~1x | 2~5x | 覆盖索引 |
| 数据安全性 | 每次 fsync | 可配置（默认全安全） | 组提交可控 |

## 六、使用建议

### 什么时候开 WAL 组提交

✅ **推荐开启**：
- 高频率小写入（如 Agent 消息逐条写入）
- 可容忍进程崩溃时丢失极少量数据（最多 group_size 条）
- OS 级崩溃概率低（服务器 / 容器稳定运行）

❌ **保持默认（禁用）**：
- 金融级数据，每条都必须落盘
- 写入频率低，fsync 开销可忽略
- 对数据丢失零容忍

### B + D 适用场景

✅ **最佳组合**：
- 有明确的高基部分区键（如 session_id、user_id）
- 查询模式以「按分区键取一批数据」为主
- 有 2~3 个高频访问的小列适合放入覆盖索引

❌ **效果有限**：
- 完全随机的查询模式
- 聚簇列基数太低（如只有 2~3 个值）
- 需要回表取大字段（如全文本 content）
