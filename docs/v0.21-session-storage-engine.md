# v0.21 会话存储引擎设计（Agent 会话内容存储）

> 日期：2026-08-07
> 状态：设计稿（待讨论确认）
> 目标：为 Agent 提供**会话内容存储**专用引擎——高性能写入、零维护
> （无 VACUUM、TTL 自动清理）、长跑不膨胀，直接对标并碾压 SQLite 会话场景

---

## 一、背景：opencode 实证调研（为什么 SQLite 时间长了会卡）

对 opencode 真实数据（`~/.local/share/opencode/opencode.db`，7.8GB SQLite）的实测：

| 表 | 行数 | 体积 | 说明 |
|---|---|---|---|
| event | 52.2 万 | **5.5 GB**（70%） | 事件溯源日志 |
| part | 55.7 万 | 1.05 GB | 消息片段（text/tool/step/patch/reasoning）|
| message | 16 万 | 747 MB | 消息（`data` 列存完整 JSON）|
| session | 292 | 0.1 MB | 会话元数据（agent/model/cost/tokens）|

### 病根 1：写放大 610×（卡顿主因）

- **平均每条消息被全量重写 610 次**（流式输出每 chunk 一次 `message.updated.1`），
  最大一条被更新 **64,688 次**、单事件峰值 3MB
- 事件日志累计 **5.04GB**，物化数据仅 1.5GB → 冗余比 ~4.5×，IO 放大 610×
- 例：单条最终 155MB 的消息 → 事件日志累计写入 5GB

### 病根 2：无清理 → 无限膨胀

- 292 会话全量保留、无 TTL/归档；WAL 持续增长；无压缩（`data` 列存完整 JSON 字符串）

### 病根 3：读路径未优化

- 加载会话 = `message` JOIN `part` 全表路径；UI 只读最新消息，但无「按会话尾部
  分页」优化；无会话全文搜索

### 结论

SQLite 会话场景的卡顿 = **流式全量重写（610×）+ 无清理（无限膨胀）+ 无压缩**。
我们的设计逐条对症（见下）。

---

## 二、设计目标

| 目标 | 手段 |
|---|---|
| 写放大趋近 1× | Log 引擎 **append-only** + part 级增量追加（每 chunk 新行，不重写）|
| 零维护 | 表级 TTL + 块级过期跳过 + checkpoint 物理释放（无 VACUUM）|
| 会话读毫秒级 | 块级 session 跳读 + 尾部读取（recent_messages）|
| 体积可控 | 长文本列压缩 + TTL 淘汰 + 过期块不落盘 |
| Agent 友好 | Rust API 优先（append_message/get_session/recent/search）+ SQL 模板 |

## 三、数据模型（两表：消息元数据 + 内容流）

```
CREATE TABLE session_messages (            -- 消息元数据（写一次，不再变更）
    session_id   VARCHAR NOT NULL,
    msg_id       VARCHAR NOT NULL,
    role         VARCHAR NOT NULL,          -- user / assistant / tool / system
    created      TIMESTAMP NOT NULL,
    is_deleted   BOOLEAN NOT NULL DEFAULT false
) ENGINE = Log WITH TTL 30d;

CREATE TABLE session_parts (               -- 内容流（追加式，每 chunk 一行）
    session_id   VARCHAR NOT NULL,
    msg_id       VARCHAR NOT NULL,
    seq          INT NOT NULL,              -- chunk 序号
    part_type    VARCHAR NOT NULL,          -- text / tool / patch / reasoning / step-start / step-finish
    content      VARCHAR NOT NULL,          -- 增量内容（非全量快照）
    is_final     BOOLEAN NOT NULL DEFAULT false,  -- 该 part 是否已结束
    created      TIMESTAMP NOT NULL
) ENGINE = Log WITH TTL 30d;
```

**为什么拆两表**：opencode 实证 part 是主体（55 万 vs 16 万）；消息元数据低频
（每条一次），内容流高频（每 chunk 一次）。分离后：
- 元数据行不随流式重写（写放大消除）
- 内容行可独立压缩、独立 TTL 淘汰
- 消息重组 = 按 msg_id 分组合并 seq 有序行

**替代方案（单表）**：消息元数据 + part 混一张表。省一次查询但流式写会混入
元数据行，且列数被迫取并集。**否决**——两表更贴合 opencode 实证负载。

## 四、写入路径（写放大 ~1×）

```rust
// 流式输出示例（一次 assistant 回答）
let msg_id = store.begin_message(&session, "assistant")?;   // 1 行元数据
for chunk in stream {                                        // 5000 个 chunk
    store.append_part(&session, &msg_id, "text", chunk)?;    // 5000 行增量
}
store.finish_message(&msg_id)?;                              // is_final 标记
```

- `append_part`：Log 引擎追加行，微秒级；**只写增量 chunk，绝不重写整条消息**
- `finish_message`：标记该 msg 最后 part 为 final（也是追加语义，无 UPDATE）
- 写放大对比（5000 chunk）：opencode 5000 × 31KB ≈ **155MB**；
  EngramDB 5000 × ~300B ≈ **1.5MB**（~100×）

**工具调用**：`tool` part 直接追加（call 与 result 各一段增量）。

## 五、读取路径

```
get_session(session_id) -> Vec<Message>
  1. session_messages 块级跳读：只扫含该 session 的块（A2 机制）
  2. 行级过滤 session_id + !is_deleted
  3. JOIN session_parts 同 session 块 → 按 msg_id 分组、seq 有序合并

recent_messages(session_id, N) -> Vec<Message>   // UI 主路径：只读最新 N 条
  1. 定位含该 session 的最后一个块（块行序 = 追加序，块尾即最新）
  2. 块内从尾部倒序取 N 行（Log 引擎块级 row_id 二分，O(1) 定位）

list_sessions() -> Vec<(session_id, msg_count)>
  1. 会话级倒排计数（session_id -> count，会话 API 层 HashMap 增量维护）
  2. 或 message 表按 session 分组扫描（块级跳读摊销）
```

**删除语义（追加式，保持 Log 引擎无 DELETE）**：
- 单消息：追加一行 `is_deleted=true` 的元数据更新行（墓碑），读取时过滤
- 整会话：`delete_session` 标记 + TTL 兜底（过期自然淘汰）
- 不产生 VACUUM/碎片——墓碑行随 TTL 淘汰

## 六、TTL 与物理淘汰（零维护核心）

- **表级 TTL**（用户已确认）：`WITH TTL 30d`，全表统一保留期
- **块级过期跳过**：块头含 created 列 MinMax（Log 引擎已有），扫描时
  `max < cutoff` 整块跳过（复用 v0.20 TTL 扫描模式）
- **checkpoint 物理释放**：过期块序列化时丢弃，文件体积不随过期增长
  （opencode 无此机制 → 5.5GB 冗余；我们 TTL 后体积趋近「活跃窗口」）

---

## 七、压缩（体积控制）

- `content` 长文本列（text/patch）：走现有压缩管线（Columnar 7 种算法；
  Log 引擎块序列化复用之），长文本 3-10× 体积收益
- `metadata`（agent/model/tokens）：独立小表，不随消息体重复

## 八、会话 API（Rust 优先，用户已确认）

新增 `src/session.rs`：

```rust
pub struct SessionStore<'a> { db: &'a mut Database }

impl SessionStore<'_> {
    pub fn open(db: &mut Database) -> Result<SessionStore<'_>>;      // 自动建两表
    pub fn begin_message(&mut self, session: &str, role: &str) -> Result<String>;   // -> msg_id
    pub fn append_part(&mut self, session: &str, msg_id: &str, part_type: &str, content: &str) -> Result<()>;
    pub fn finish_message(&mut self, session: &str, msg_id: &str) -> Result<()>;
    pub fn get_session(&mut self, session: &str) -> Result<Vec<Message>>;
    pub fn recent_messages(&mut self, session: &str, limit: usize) -> Result<Vec<Message>>;
    pub fn list_sessions(&mut self) -> Result<Vec<(String, u64)>>;
    pub fn delete_message(&mut self, session: &str, msg_id: &str) -> Result<()>;   // 墓碑
    pub fn delete_session(&mut self, session: &str) -> Result<()>;                 // 墓碑 + 清理索引
    pub fn search_messages(&mut self, query: &str) -> Result<Vec<Hit>>;            // A4 倒排
    pub fn set_ttl(&mut self, seconds: u64) -> Result<()>;                          // 运行时调保留期
}
```

SQL 模板（文档提供）：两表建表语句 + 4 个查询示例（按会话取、最近 N、计数、搜索）。

## 九、A4 会话全文搜索（倒排）

- `session_parts` 维护词 → (session_id, msg_id) 倒排索引（v0.18 inverted_index
  复用；CJK 分词留 v0.22 B3）
- `search_messages(query)`：分词 → AND/OR 求交 → 映射回会话
- 倒排随追加更新（Log 引擎 append-only 天然适配）；TTL 淘汰时同步清理词条

## 十一、依赖与风险

| 项 | 说明 |
|---|---|
| A1 Log TTL | capabilities.rs 开启 + 块级 cutoff（复刻 v0.20 TTL 三路扫描模式）|
| A2 session 跳读 | LogBlock 增 `sessions: HashSet<Value>`；`block_can_skip` 扩展 Eq 谓词 |
| A3 API | 新模块，两表自动建表 |
| 风险：Log 引擎单谓词下推 | session 等值走 skip_pred（TTL 是引擎内置，不占谓词位）→ 可共存 |
| 风险：倒排内存 | 10 万会话规模可控；超限可降级为扫块（基准验证）|
